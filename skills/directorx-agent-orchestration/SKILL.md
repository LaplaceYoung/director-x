# DirectorX Agent Orchestration

Use this skill as the subagent control surface for DirectorX production runs.

## Workflow

1. Read the current Run's generated `Director.md`, `references/subagent-prompt-tool-contract.md`, and the task-specific bundled DirectorX skill docs. When developing inside the DirectorX source repository, `docs/directorx-subagent-orchestration-pack.md` is optional deeper context; installed plugin operation must not depend on it.
2. Build parallel research waves from distinct domain owners instead of assigning one generic review capability to every role. Use `reference.retrieve` or `reference.temporal_ground` for `DX-Reference-Analyst`, `asset.audit` for `DX-Asset-Manager`, and `review.candidate_search` or `review.av_sync` for `DX-Quality-Reviewer`. A capability's catalog owner is authoritative.
3. Prefer `directorx_plan_production_team` after complexity and execution-graph registration. It derives bounded DX tasks from authoritative graph ownership and returns the same executable host actions without requiring the parent agent to hand-author a task array. Use `directorx_plan_parallel_subagents` only for an intentionally custom delegation graph. Spawn only the returned host actions. The generated prompt already identifies the active project path, Run ID, artifact directory, and immutable delegation depth `1/1`. A delegated DX agent is inside an existing production Run: it must not invoke `@directorx`, rerun preflight, create another Goal/Run, install roles, open another canvas, request a Codex restart, call `spawn_agent`, call either planning tool, or use any skill/tool that creates another background agent.
4. Classify the request into a workflow: `commercial_short_video`, `product_ad`, `reference_to_video`, `repair_export`, or a custom pipeline manifest.
5. Select the smallest complete subagent set from the design-book modules: task planner, director runtime, reference analyst, shot planner, asset manager, provider operator, model router, cost controller, draw-loop controller, memory manager, quality evaluator, editing agent, and approval producer.
6. Assign the canonical `DX-xxxxx` identity before delegation. All Director X subagents, artifact owners, handoffs, canvas nodes, and status messages must use a name returned by `directorx_list_subagent_roles`; never expose an unprefixed internal role as the production identity.
7. For each subagent, define required input artifacts, output artifacts, tool access, stop condition, escalation triggers, cost/attempt cap, and approval boundary before execution.
8. Read the exact current Codex `spawn_agent` schema and register the executable DAG. Pass its `agent_type.enum` values as `availableAgentTypes`, or pass `["collaboration_task"]` when the host instead exposes `task_name/fork_turns/message`. The planner prefers native `dx_*` roles, then built-in typed hosts, and also supports collaboration-task hosts whose thread identity arrives through `sub_agent_activity`. It rejects unroutable roles, duplicate output owners, duplicate live roles, cycles, and fake parallelism, then splits broad dependency layers into capacity-bounded waves.
9. Once a wave's `requiredStage` is active, dispatch every `spawn_agent` action carrying the same `parallelGroupId` before awaiting any individual result and execute its exact `afterSpawn` action. Typed hosts use `{ agent_type, message }`, then close with `{ target: hostAgentId }`. Collaboration hosts use `{ task_name, fork_turns, message }`, register the matching `sub_agent_activity.agent_thread_id`, and become released only after the terminal activity event; never invent a `close_agent` call that the host does not expose. Registration, terminal, release, and overlapping timestamps must persist in `parallel_subagent_dispatch.json`; planning multiple agents is not evidence of parallel execution. Only after every prior-wave artifact and host-release barrier passes may the next wave register. On a resumed turn, execute actions from `directorx_get_run_snapshot.resumeActionPlan` so running/bound tasks are never spawned twice. The default research wave pairs `DX-Reference-Analyst` with `DX-Asset-Manager`; add `DX-Model-Router` when official API adaptation owns a distinct provider-adapter artifact.
10. Write or update `pipeline_manifest.json`, `tool_registry.json`, `decision_log.json`, and the stage artifacts owned by each subagent. Transition graph nodes alongside subagent status so canvas progress reflects artifact dependencies, not only agent presence.
11. Keep prompts artifact-facing: every output must be a structured artifact, memory patch, provider request, review decision, approval gate, or export instruction.
12. Validate the handoff: downstream consumer exists, tool access is scoped, cost/attempt caps are explicit, approval gates are recorded, and every declared output is registered before marking the DX task complete.

## Codex Naming Contract

- Before the first delegation in a project, call `directorx_get_subagent_naming_status` with the detected host contract. Treat `diskReady`, `customSessionReady`, `compatibilitySessionReady`, and `collaborationTaskSessionReady` separately. `sessionReady=true` is sufficient for production: native `dx_*`, built-in typed, and collaboration-task hosts all preserve canonical DX identity through the delegated prompt, registry, artifacts, and canvas. Install custom roles only as an optional naming enhancement or when no compatible host exists.
- Before spawning, call `directorx_list_subagent_roles` and choose the canonical identity for the role.
- Call `directorx_plan_production_team` before the first spawn and treat its `hostActions` as required Codex host actions, not advisory text. The manual `directorx_plan_parallel_subagents` route is only for a custom graph that cannot be represented in `execution_graph.json`.
- A Run owns one immutable top-level delegation plan. Reusing the same `planId` is idempotent; replacing it or allowing `spawn_agent`, `directorx_plan_parallel_subagents`, `create_thread`, or `create_goal` inside a delegated task is a runtime error.
- Spawn with the exact `agentType` returned by the plan. It may be the native `dx_shot_planner` or a role-appropriate built-in compatibility host.
- Start the delegated prompt with: `Director X identity: DX-xxxxx.` Require that exact identity in artifact ownership and result messages.
- After `spawn_agent`, enforce the plan's `hostNicknamePolicy`. Native DX hosts accept only the catalog `displayName` or Codex's ordinal variant. A built-in compatibility host may return its own nickname; retain it only as trace metadata and bind the plan's canonical `displayName` through `directorx_register_subagent`.
- Use `directorx_update_subagent` for running, blocked, complete, and failed transitions. The Director X canvas and durable Run treat the DX identity as authoritative; the host nickname is trace metadata only.
- A terminal update on a typed host returns a required `close_agent` action. Execute it with `target` set to the registered host ID, then call `directorx_confirm_subagent_host_closed`. A collaboration-task host has no close action; accept release only from its terminal `sub_agent_activity` evidence.
- A stage cannot close while one of its planned DX tasks is pending, running, blocked, failed, or awaiting host release, and a task cannot complete before its declared artifact handoff is registered. Do not infer execution from the plan: inspect `parallel_subagent_dispatch.json` and the Activity batch projection.
- Reject aliases without the `DX-` prefix and reject role names that differ from the catalog.

Codex does not accept a per-call `nickname` argument. Director X installs optional custom roles under `.codex/agents/`, each with one `DX-*` nickname candidate, but production no longer waits for a restart when a built-in typed or collaboration-task host is available. The host nickname or task path is explicitly non-authoritative: the unsuffixed catalog identity remains authoritative everywhere the user or downstream artifacts can see. Only one live agent may hold each canonical role; typed hosts require close/confirm, while collaboration hosts require a matching terminal activity event before reuse.
