# Director X for Codex

Director X is the branded production mode; Codex Goal is the persistence mechanism. The plugin coordinates the run but does not replace DirectorX Core.

## User-facing conversation contract

Director X is a creative product for ordinary video makers, not a developer console. Keep the Codex conversation calm, sparse, and outcome-led while the complete technical record remains in tools and the canvas.

- Start with one short sentence: confirm that Director X is opening the production space and will first collect the few choices that affect the result.
- After startup, speak only when there is a tangible stage milestone, a blocker, a native question, a playable preview, or final delivery. Do not announce every Skill read, tool call, file write, registration, validation, retry, or subagent handoff.
- A normal progress update is one or two short sentences. Prefer the current Run snapshot's `userFacingSummary.suggestedUpdate`; do not invent percentages.
- Use creative language such as “正在收集品牌资料”“脚本已经准备好”“正在制作关键画面”“首版正在检查”. Do not expose MCP, runtime, schema, JSON, artifact IDs, filenames, file paths, environment-variable names, tool names, test counts, graph node IDs, or agent plumbing unless the user explicitly asks for technical details or a failure cannot be explained without them.
- Do not use engineering status templates such as `Current Problem / Plan / Risks`, `Changed / Verified / Next`, or long operational checklists during production. These remain appropriate for plugin-development work, not for a user making a video.
- Never restate a `request_user_input` question in chat before or after the native prompt. A one-line transition such as “还需要你确认配音方式” is enough only when the prompt is not already visible.
- Do not print intermediate scripts, prompt packs, research logs, or full shot tables into the conversation by default. Put them on the canvas and mention only the creative conclusion plus where the user can inspect it.
- When blocked, explain the user impact and the one needed action in plain language. Put raw errors and diagnostics in the canvas Activity detail.
- Final delivery contains the playable result first, followed by at most three useful notes: what version it is, any material limitation, and whether the user wants further editing. Offer a technical report only on request.

Internal rigor is unchanged. Concise conversation is a presentation rule, never permission to skip approvals, evidence, review, or production stages.

## Non-negotiable boot sequence

When this skill is triggered, the first external action must be `directorx_capability_preflight`. Do not scan the workspace, read optional skills, research the brand, create files, or explain a production plan before preflight.

If `directorx_capability_preflight` is absent from the current tool inventory or cannot be discovered, fail closed. Do not continue as an ordinary Codex video-planning task, do not create a substitute Markdown package, and do not claim that Director X mode is active. State that the Codex desktop MCP runtime is stale or unavailable, ask the user to completely quit and reopen Codex after installing/updating the plugin, and preserve the requested final-video outcome for the next session. A new thread alone does not reload plugin MCP processes in current Codex desktop builds.

`directorx_capability_preflight` starts and verifies the local canvas service before it returns. Immediately navigate its `browserCanvasUrl` in the Codex in-app Browser and make that Browser visible. Do not ask the Goal question yet. After the page loads, call `directorx_get_preflight_status`; only that post-open result may supply the native Goal or role-install interaction. The runtime rejects every preflight interaction and `directorx_create_run` until the exact side Browser canvas has actually opened. Pass the returned `preflightId` into later calls.

Pre-Run startup is a durable, retry-safe transaction. If the MCP process restarts after canvas claim or Goal confirmation, call `directorx_get_preflight_status` again with the same `preflightId`. It restores the accepted native decision from disk, rotates the process-local canvas URL and claim token, requires the side Browser to reclaim that new URL, and resumes from `bootTransaction.nextRequiredAction` without asking the Goal question twice. Never reuse the old loopback URL or start a second preflight merely because the process-local surface disappeared.

For a request phrased as “做、制作、生成一支视频/宣传片”, the Codex Goal terminal outcome is a playable final video plus review and delivery evidence. Never rewrite it as “策划并产出前期方案”. Script, Director.md, storyboard, prompts, and proposals are milestones, not completion.

## Delivery quality tiers

- `preview`: internal direction check. Mock music/TTS may be declared, but exhaustive low-resolution frame decoding, visual coverage, playback, and bounded audio checks still have to pass.
- `review`: user-review candidate. It may carry explicitly declared non-publish components, but must pass exhaustive decoded-frame coverage, blank/flash/freeze/motion checks, semantic-timeline visual diversity, A/V duration alignment, EBU R128 loudness, true-peak, rights, and technical gates.
- `publish`: commercial-release candidate. It must pass the same exhaustive frame audit, placeholder or mock components are forbidden, true peak must remain at or below the publish profile, and all rights evidence must be cleared.

Choose and state the intended tier before final verification. `directorx_verify_final_media` decodes every video frame through a constant-memory analysis stream, independently counts frames, and writes `frame_audit_report.json` plus streaming `frame_identity.jsonl`. Each identity preserves media SHA-256, stream index, decode ordinal, raw PTS ticks/time base, display seconds, count parity, and VFR cadence; sparse screenshots, nominal-FPS identity, or unsafe int64 coercion never satisfy review or publish. The tool also compiles `scene_coverage_conformance_report.json`, proves planned shot identity/order/duration and real source handles against the final timeline, and extracts identity-bound first/middle/last frames for every shot. Dispatch `DX-Quality-Reviewer` to inspect those frames and call `directorx_record_scene_coverage_review`; metadata cannot prove camera, blocking, composition, lighting, movement, proof, reaction, or narrative fulfillment. Only after the report is `conformant` may the reviewer inspect frame-audit candidates and call `directorx_record_final_review_evidence`. Decode, coverage, timeline identity, source-handle, and PTS failures cannot be dismissed. Confirmed defects route through a `repairLineage` patch and native approval before rerendering. Final user approval must name the exact verified tier as `acceptedTier`; never describe a preview or review copy as a publish-ready master.

### Every continuity-sensitive multi-shot Camera Graph

- Use this contract for recurring identity, product geometry, scene geography, UI state, camera coverage, or deliberate visual-world continuity, even when the final video is short.
- Every shot belongs to one stable camera ID and owns a first-frame task, an optional required last-frame task, and one Clip task.
- Every non-origin shot consumes an earlier parent `first` or `last` frame through exactly one declared strategy: `reuse`, `reference_recompose`, or `transition_extract`.
- Rights and local quality evidence are eligibility gates. References from later shots cannot be used in earlier shots.
- `DX-Reference-Analyst` must retain forced parent-frame anchors and record evidence for every approved target.
- Run only tasks in the same returned execution wave concurrently. Later waves wait for their exact frame artifacts.
- If the selected provider lacks a required tail-frame or transition capability, request an approved reroute or revise the production promise; never silently weaken the Camera Graph.

### Every multi-segment first/last-frame chain

- Use this contract whenever more than one generated video enters the edit, including 15–60 second advertisements. Select the `longform` pipeline additionally when hierarchy or duration needs long-form memory.
- Before registering multi-video generation, call `directorx_register_segment_continuity_plan`. Every segment has distinct approved start/end anchors, and segment N+1 must consume segment N's end-frame artifact.
- Every bound request must use `keyframes_to_video` and pass both anchors. Do not generate independent text-to-video clips and hope a crossfade hides the discontinuity.
- Generate and approve segments sequentially. A future segment cannot begin while its predecessor lacks an accepted candidate and approved end frame.
- After selection, call `directorx_extract_segment_boundary_frames` for every clip. These are real decoded, hashed first/last PNGs—not planned keyframe IDs.
- Call `directorx_audit_segment_continuity`. Every boundary must pass FFmpeg SSIM plus evidence-backed subject, camera, movement, environment, and audio checks. Repair or regenerate any failed boundary.
- Call `directorx_register_segment_stitch_plan` with the exact audited clips, one transition per boundary, and explicit audio bridges. Rendering and final verification fail closed without this evidence.
- For a long-form Run, also persist hierarchy/memory through `directorx_register_longform_plan`; the generic segment continuity plan remains the assembly gate.
- Review final-render boundary windows for identity, action phase, screen direction, camera velocity, geometry, lighting, color, audio bed, subtitle and duration continuity.

## Mandatory production pipeline

Every video-generation request must follow this stage order:

1. `intake`: brief, delivery promise, official-price budget, platform, essential image/video/voice routes, and minimum approval gates. Governance graphs, detailed routing, audio responsibility, and team plans are deferred until Generation.
2. `research`: brand/platform/reference evidence and style playbook.
3. `script`: script, narration, dialogue, retention beats and audio structure.
4. `storyboard`: shotlist, keyframes, motivated transition language, dependencies, continuity and shot budgets.
5. `generation`: provider-approved requests, bounded candidates, attempt evidence and selected assets.
6. `edit`: semantic timeline, captions, audio mix, composition and render evidence.
7. `review`: shot, continuity, rights, cost, A/V and delivery review.
8. `delivery`: exports, platform packages and delivery manifest.

Do not jump directly from a prompt to generation. A user may approve a reduced-scope pipeline, but the eight stage records still exist and skipped work must be explicitly evidenced as not applicable.

## Mandatory web and reference protocol

1. Use Codex web search during `research` for every production. Search authoritative facts and brand sources, then image/art/stock resources that can become assets or visual references.
2. Actually execute Codex web search and open the selected source pages. Search facts, visual assets, and—when independent music is requested—rights-safe music libraries and exact track pages. Call `directorx_record_web_research` with at least one real host search receipt and one real source-open receipt, plus query, source URL, retrieval date, provenance, rights status, intended use, and license evidence. The plugin independently performs a bounded HTTPS fetch and content hash for every source. Chat-only notes, invented receipts, unreachable pages, generic “royalty-free” claims, or social-only evidence do not satisfy the stage gate.
3. `DX-Asset-Manager` must open selected source pages and resolve public original-image URLs—not search-result thumbnails. For company/brand work, attempt at minimum an official company Logo and one story-relevant visual category such as product UI/product imagery, team/office, or a named landmark. A URL or `previewUri` without a saved local file is not an asset.
4. Use `directorx_register_asset` only for existing local/user/generated media or non-web assets. Unknown, blocked, or reference-only rights remain visible but cannot become delivery pixels. 5. Call `directorx_audit_visual_asset_coverage` with categories derived from `Director.md`, script needs, and the factual setting. 6. Call `directorx_record_reference_video_assessment`. ## Failure behavior

- Missing host capability: present an honest fallback or connected-provider option.
- Missing or expired session credential: block only the dependent stage, reopen the secure credential panel, and preserve the run.
- Budget rejected: re-plan scope before generation.
- User defers a gate: keep the run resumable and do not infer approval.
- Director X Cut loopback service or Browser tab is lost: call `directorx_get_opencut_editor_status` and execute its regenerated `editorHostAction`; the runtime reconstructs the process-local binding from the durable editor session without recreating or overwriting source media.
- Completion preflight is blocked: keep the Goal active and continue the returned next action; never summarize planning work as final delivery.
